# Welearn 学时/completion 被清空、被打回的原因调研（ANTICHEAT RESEARCH）

> 调研对象：`welearn.sflep.com`（上海外语教育出版社 WE Learn / 随行课堂）及其各校部署
> 现象：**当天显示"已完成"，次日或数日后进度/时长消失，或被任课教师打回重做**
> 版本：2026-11 · 与 `docs/PROTOCOL_FORENSICS.md`（本地实测协议取证）配套阅读
> 方法：GitHub 开源实现源码与 issue 一手材料 + 高校教务/通识学院成文规定 + 同类平台（超星/尔雅、智慧树）横向规则 + 本仓库抓包实证

---

## 一、结论摘要（哪些情况会被清 / 被打回，按概率排序）

概率是"在本项目当前实现（10 线程 + 单课时 60~120s + 纯发包 + 每请求随机 UA）下，触发该原因"的经验估计，不是平台公布值。

| # | 原因 | 概率 | 触发层 | 典型症状 |
|---|---|---|---|---|
| 1 | **时钟流速校验**：单课时实际墙钟 60~120s，而课件自身声明时长 `timelitsec` 通常为 1080s（18min），比值约 6%~11% | ★★★★★ | 服务端自动 | 时长不计入 / 学时被扣 / 次日 `learntime` 归零 |
| 2 | **全账号短时间集中完成**：几十个小节在几分钟~几十分钟内全部 completed | ★★★★★ | 服务端自动 + 教师可见 | 整门课进度回滚，或课时列表大面积变"未完成" |
| 3 | **纯发包请求特征**：无浏览器 JS 环境、无 SPA 资源加载序列、TLS/JA3 与 UA 不匹配、密码登录绕过浏览器指纹 | ★★★★☆ | 服务端自动 | 当天成功、次日清零；严重时账号被限 |
| 4 | **并发多开互踢**：服务端单点会话令牌 `studyTicket` + `StudyCourse.aspx` 心跳互踢，后开的把先开的踢掉 | ★★★★☆ | 服务端自动 | 部分课时时长丢失 / 完成状态被后一次提交覆盖 |
| 5 | **心跳缺失或间隔超限**：间隔 ≥60s 时短课时一次都不触发；只 `startsco`+`savescoinfo` 全程不心跳 | ★★★★☆ | 服务端自动 | 显示完成但时长为 0 |
| 6 | **正确率与作答明细不匹配**：`crate=100` 但 `interactions` 为空/条数远少于题量 | ★★★☆☆ | 教师审计 | 成绩被老师手工清除（"直打后端"被识别） |
| 7 | **教师端复核**：正确率过高、学习时长太短、进度突进 → 进入「需要关注学生」清单 | ★★★☆☆ | 人工 | 被打回重做、形成性评价记 0 |
| 8 | **校级/平台制度性清零**：同类平台明文的"次日清空""异常记录清除""多次异常冻结" | ★★☆☆☆ | 管理侧 | 全学期记录清空、取消考试资格 |
| 9 | **误判与重算**：课程内容重新发布（SCO 版本更新）、学期/班级重排、退班重进 → 进度被重算 | ★★☆☆☆ | 系统 | 部分旧课时变未完成，时长不动 |
| 10 | **深夜/7×24 连续运行**：00:00–06:00 高频心跳、单日 12h+ 有效时长 | ★★☆☆☆ | 服务端自动 | 异常标记，配合 #1#2 一起命中 |

**一句话**：不是"提交得对不对"的问题，而是**"提交所耗的真实时间对不对"**。Welearn 的学时由服务端按墙钟差累加（`learntime = t2 - t0`，见 §1.3 实测），客户端上报的 `session_time`/`total_time` 大值一律不认。因此任何"用 90 秒干完 18 分钟的活"的实现，都天然落在风控正面。

## 三、可落地的规避参数

> 原则：**让每个课时的"真实耗时"落回课件声明时长的合理区间，并让账号行为在时间轴上像一个人。** 参数按"必须 / 强烈建议 / 可选"分级。

### 3.1 单课时时长（最重要）

| 项 | 建议值 | 依据 |
|---|---|---|
| 下限（必须） | `max(300s, 0.5 × timelitsec)`；实测按 **≥480s** 起步最稳 | E10 声明 1080s；E8 同行门槛 60~90s 仅为"保底"，其目标总时长分摊后实际远高 |
| 推荐区间 | **600~900s**（10~15min），按课程权重分摊 | E8 `target_total_seconds` 分摊 + ±35% 抖动 |
| 上限（必须） | **≤1800s**（30min） | E13 平台单页面最多 30min，超时会话失效、该段不算 |
| 分配方式 | 全课程目标总时长先算净差额，再按"每节题量/文本长度"加权分摊，权重乘 `1±0.35` 随机 | E8 |

> 若目标总时长不足（如 40 节 × 600s = 6.7h 而学期要求仅 4h），**不要压缩单节**，而是减少本次处理的小节数。

### 3.2 心跳

| 项 | 建议值 | 依据 |
|---|---|---|
| 间隔（必须） | **20~32s 随机**，硬上限 <55s | E12（>60s 归零） |
| 次数（必须） | `≥ ceil(learntime/32) + 2`（开工一次 + 收尾一次） | 同上 |
| 字段（必须） | `session_time` 与 `total_time` 严格随墙钟**单调递增**，`total_time = init_total + elapsed` | E10/E11 |
| 禁止 | 一次传大值（99999）、跳变、回退、并发心跳同一 SCO | E10、E7 |

### 3.3 并发

| 项 | 建议值 | 依据 |
|---|---|---|
| 线程数（必须） | **1**（串行）；绝对上限 2，且必须是不同 SCO、不同单元 | E7 `studyTicket` 互踢：并发只会互相覆盖，净收益为负 |
| 线程启动错开 | 已无意义（串行）；若为 2，错开 ≥30s | — |
| 同一 SCO 重复提交 | 0 次（客观题只允许提交一次，`cci.retry_count` 会自增） | `docs/PROTOCOL_FORENSICS.md` §6.3 第 10 行 |

### 3.4 单日 / 批次节奏

| 项 | 建议值 | 依据 |
|---|---|---|
| 单日有效时长上限 | **≤6h（21600s）**；新手/风险期 ≤3h | E17/E18 复核看"当日异常密度" |
| 单批次节数 | **3~5 节**，批间休 **10~25min 随机** | E5 维护者建议"每次只过一两章、把时间周期拉长" |
| 单日批次 | ≤4 批，且批次开始时间随机漂移 ±40min | 同上 |
| 全课程铺开 | 总节数 / (3~5) ≈ 所需天数，**不在一晚跑完**；每日节数上下浮动 30% | E5/E8 |
| 时段窗口 | **08:00–23:00**，避开 00:00–06:00 | E21 |
| 会话连续性 | 单次连续运行 ≤90min，之后"休息"≥20min 再继续 | 真人学习画像 |

### 3.5 设备与请求特征（自证"我是浏览器"）

| 项 | 要求 | 依据 |
|---|---|---|
| UA | **整个会话固定一个 UA**（与之匹配的 `sec-ch-ua`/`Sec-CH-UA-Platform` 一并固定）；**禁止逐请求轮换** | 逐请求换 UA 是同源 session 内的强异常信号；E4 说明指纹层已被审计 |
| 请求头 | 保留 `Sec-Fetch-Site/Dest/Mode/User`、`Origin`、`Referer`（指向真实上级页面）、`Accept-Language` 固定中文 | — |
| 会话前置 | 登录后先走真实页面链路（课程列表 → 课程主页 → 单元页 → SCO 页），再开 `startsco` | E6 请求特征审计 |
| TLS 指纹 | 理想为 `curl_cffi`/`tls_client` 的 chrome 指纹；缺失此项属**无法完全规避**（见 §四） | E4 |
| IP | 单账号单出口，避免频繁换 IP/跨国出口 | E19 设备与登录时间可见 |

### 3.6 内容自证字段（提交时必须有、且互相一致）

| 字段 | 要求 | 依据 |
|---|---|---|
| `cmi.completion_status` | `completed` | E1 |
| `cmi.progress_measure` | `"1"` | E1 |
| `cmi.mode` | `normal`（**不可 browse**，browse 会短路自动完成且通常不计时长） | §6.3 第 6 行 |
| `cmi.session_time` / `total_time` | 与墙钟一致、递增 | E10 |
| `cmi.interactions` | **条数 = 实际题量**，`learner_response` 走 `escape()`；空 interactions 会被判"课时完成但无作答记录" | §6.3 第 7 行、E6 |
| `crate` | **75~92%**，且与 `interactions` 的 `result` 分布自洽（`wrong` 条数 ≈ 题量×(1-crate)） | E9（100% 最扎眼） |
| `trycount` / `cci.retry_count` | `0`，且不重复提交 | §6.3 第 10 行 |
| `startsco → setscoinfo` 间隔 | `≥ max(30s, 0.98 × learntime)` | E11 |
| 提交后回读 | `getscoinfo_v7` 校验 `learntime` 已增长；未增长则本次标记失败（不要盲目重试超过 1 次） | E3 |

### 3.7 抖动规范

- 所有固定间隔改 `lognormal(μ, σ=0.25)` 或 `uniform(0.65x, 1.35x)`（E8 的 ±35%）；
- 单课时时长、批间隔、批次内节序都加抖动；**不要出现"每 60 秒整"的等距脉冲**（心跳间隔也一样）。

## 四、无法规避的部分（必须说清）

1. **1:1 的物理时间下界**。学时 = 服务端墙钟差（E10/E12），"想拿 6h 学时就必须真的在线 6h"，没有任何参数能压缩这条。所有"加速"手段只能提高**单位在线时长的完成节数**，不能提高学时本身。
2. **单点会话互斥**。`studyTicket` 互踢是服务端结构设计（E7），并发在数学上是负和：多开不会让总学时变多，只会丢。
3. **`interactions.latency` 等服务端折算字段**。由会话时间反推（E16），客户端伪造无效；伪造 `latency` 反而制造"答题速度与耗时矛盾"。
4. **浏览器 JS 环境特征**。纯 HTTP 客户端没有 canvas/WebGL/字体/时序/`performance.now()` 抖动，也没有真实 DOM 事件流；做到最好也只是"TLS+头部像浏览器"，**成不了浏览器**。这是纯发包方案与 DOM 方案稳定性差距的根（E5/E6）。
5. **教师人工审计**。教师端能看到"最近登录时间 / 每次登录与完成时间点 / 按天周月时长 / 设备构成"，并能把时长设成考核权重（E19）；`100% 正确率 + 每节 90 秒 + 一晚做完 40 节` 这种组合，人工一眼可辨（E9 明说"老师审计并清除成绩"）。
6. **校级制度与处罚阶梯**。"次日清空 / 异常记录清除 / 冻结 / 取消考试与考试资格"是管理侧行为（E17/E18），技术上不存在规避面；这部分风险只由"行为像人"降低概率，不能归零。
7. **平台迭代**。E15 的"脚本已失效且永不更新"、E6 的"已上线请求特征审计"说明对抗是持续的；任何参数都是**当前时点的最优解**，不是永久解。
8. **不可逆的锁**。客观题"只能提交一次"（`cci.retry_count` 自增），一旦用错答案提交即无法回改；出现"学习数据不正确"后重试窗口也有限（E3）。
9. **内容重发布导致的重算**。SCO 版本更新、学期/班级重排会把旧完成标记重算（E20 提到记录与课程绑定），与行为无关，无法预防。
10. **录屏/摄像头/人脸核身**（Welearn 当前未见，但同类平台已在校内考试环节使用）。一旦引入，纯自动化方案整体失效。

## 五、建议写入程序的默认值（对照 `src/welearn_gui.py`）

| 参数 | 现值 | 建议默认值 | 位置 |
|---|---|---|---|
| 刷课线程数 | `10` | **1** | `welearn_gui.py:1181`（`curriculum_max_threads`）、`:1465` 输入框默认 |
| 刷时长线程数 | `10` | **1** | `welearn_gui.py:1186`（`time_max_threads`）、`:1465` |
| 单课时时长 | `[60, 120]` 秒 | **[600, 900]** 秒 | `welearn_gui.py:1180`、`:1184`、`:1452`、`:1456`（输入框 60/120 → 600/900） |
| 心跳间隔 | `randint(30, 40)` | **`randint(20, 32)`** | `welearn_gui.py:910`、`:924` |
| 批次间间隔 | `0.3~0.5s` | **每 3~5 节后 600~1500s** | `welearn_gui.py:821`、`:977` |
| 正确率默认 | `100` | **88**（范围 75~92） | `welearn_gui.py:1178`、`:1411`、`:1424` |
| UA 策略 | 每请求 `_random_ua()` | **会话级固定**（session 建立时取一次，`_build_headers()` 复用） | `welearn_gui.py:60`、`:63-85` |
| 时段窗口 | 无 | **08:00–23:00**（窗口外暂停） | 新增，`thread_time_execute` / `thread_curriculum_execute` 入口 |
| 单日预算 | 无 | **有效时长 ≤21600s，节数 ≤24** | 新增，需本地持久化计数 |
| 单批次节数 | 无（=线程数） | **3~5 节** | 新增，批次循环处 `:719`、`:870` |
| `startsco→setscoinfo` 下限 | `learntime` | **`max(30, 0.98×learntime)`** | `welearn_gui.py:394-405` |
| 提交后回读校验 | 无 | **`getscoinfo_v7` 校验 `learntime` 增长，失败仅重试 1 次** | 新增于 `:412` 之后 |
| 单 SCO 提交次数 | 未限制 | **硬性 1 次/SCO/会话** | 新增 |

> 若把默认值改成"1 线程 + 600~900s/节 + 08:00–23:00 + 每日 ≤6h"，则 40 节的课程需要 **2~3 天**才能跑完，这是与"不被清空"直接等价的代价，UI 上应显式告知用户（预计耗时天数）。
