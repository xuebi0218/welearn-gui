# Welearn 刷课后「记录被清 / 隔天打回」风险分析与对策

> 适用版本：v3.6
> 结论基于两部分证据：① 平台前端代码（`tools/studycourse.html` 4470 行、`tools/lms.js` 64KB 官方 LMS 实现）静态分析；② 用真实账号对 `Ajax/SCO.aspx` 各 action 做的实测（含伪造时长、心跳间隔、并发、票据互斥）。
> 本文只讲机制与对策，不含任何站点攻击内容。

---

## 一、先看结论

| 现象 | 真正原因 | 概率 |
|---|---|---|
| 当天显示「已完成」，第二天变成「未完成」/时长归零 | 平台**日终批处理**：完成事件当天入库，T+1 再跨事件聚合复核（完成密度、心跳连续性、时长/要求比），命中就整批回滚 | ★★★★★ |
| 时长永远不涨，只有完成状态 | 心跳缺失或间隔 > 60s，服务端按「两次心跳的墙钟差」累计，漏掉的那段直接丢弃 | ★★★★★ |
| 完成很快，但过几天被老师清掉 | 正确率 100% 却没有答题记录（interactions 为空/偏少），命中教师端「学习监控 / 需要关注学生」 | ★★★★☆ |
| 多开几个窗口后时长反而更少 | `studyTicket` 是**单账号互斥锁**，多个 SCO 并发会互相 `EndSCO`，分钟数互相顶掉 | ★★★★☆ |
| 突然被锁 N 分钟 / 今日锁定 | 服务端 `action=isPausing` 判定「刷课行为」，唯一显式封禁通道 | ★★★☆☆ |
| 打开课件就卡住、脚本不动 | `action=checkNoCaptcha` 返回 `status=0`，要求滑块验证 | ★★★☆☆ |

**一句话**：平台判的不是「你提交了什么」，而是「**你花了多少真实时间**」。

> **v3.7 追加实测（2026-11-20）**：`studyTicket` 互踢只发生在浏览器 JS 层（多开标签会弹框并 `EndSCO`），
> 纯 HTTP 发包不受这一层约束：4 路同时提交，4 个课时各自 +61s（墙钟 86s），**零损耗、无闸门触发**。
> 也就是说——学时确实不能压缩，但可以**并行赚**：4 路并行 = 墙钟摊薄 4 倍。
> 这就是「绕过早慢」的唯一真实解，且它与「真实时长」并不冲突。
学时是物理量，任何参数优化只能提高「单位时长内的完成节数」，不能把 18 分钟的课压成 90 秒。

## 二、平台是怎么计时的（代码级证据）

1. **服务端主导计时**
   `startsco160928` 返回 `{"ret":0,"timelitsec":1080,"useSeconds":517,...}`：
   - `timelitsec` = 该课时要求的学习秒数（实测多为 1080s = 18 分钟）
   - `useSeconds` = 已累计的有效秒数
   - `useSeconds >= timelitsec` 时返回 `endcaltime:true`，停表

2. **客户端上报的时长不被信任**
   把 `session_time` 改成 600/1200、`total_time` 改成 1121/1721，服务端只回 `seconds:1`。
   真正入账的是服务端自己按墙钟算出来的增量。

3. **心跳才是计时的开关**
   `keepsco_with_getticket_with_updatecmitime` 的响应形如
   `{"ret":-1}{"ret":0,"seconds":30,"endcaltime":false,"ticket":"…"}`。
   - `ret==0` 才给 `seconds`（服务端授予的增量）
   - `ret==1` = 计时被复位，不累加
   - 官方页面是 `setInterval(KeepLearnTimeAndCheckToken, 60000)`，即**60 秒一次**
   - 漏发心跳 → 那段时长不进入 `useSeconds`

4. **完成判定只看两件事**
   `cmi.completion_status = completed` 且 `progress_measure = "1"`。
   与答题数量、正确率无关；`success_status` 前端从不设置（恒 `unknown`）。
   所以「完成状态」很容易拿到，**难的是时长**——这也是为什么风控盯的是时长。

5. **"学习数据不正确" 是服务端消息**
   触发面只有两个：`getscoinfo_v7` 无会话；`startsco → setscoinfo` 墙钟差 ≈ 0。
   后者会让 `setscoinfo` 失败但 `savescoinfo` 仍成功 → 课时显示完成、答题记录全丢。

6. **平台没有「切屏检测」**
   `sco_main.js`、`lms.js` 中 `visibilitychange` / `document.hidden` / `pagehide` 命中数为 0。
   唯一的离开钩子是 `onbeforeunload → terminate()`，只清会话状态，不上报字段。
   但**有无操作检测**：`CheckActive()` 每 60 秒检查最后活动时间，超过 30 分钟 → `EndSCO(true)` + alert + 跳回主页。
   纯 HTTP 复刻不跑那段 JS，因此不受影响。

## 三、什么情况下会被「打了又回滚」

### 1. 时钟流速异常（最常见）
单节课真实耗时 60~120 秒，而课件自声明需要 1080 秒，比值只有 6%~11%。
一小时刷完十几节课、`useSeconds` 却刚好卡在 `timelitsec` 附近，特征极其明显。

### 2. 短时间集中完成
一天内几十节 `completed` 挤在几十分钟里，且 `learntime` 出现**完全相同**的秒数（不同课时同一秒）——
这是脚本的指纹。

### 3. 心跳断档
课时要求 1080s，但整段学习过程中一次心跳都没发（或间隔 > 60s），时长直接记 0。
v3.4 修复的正是这个；v3.6 进一步把心跳提前到 20~32 秒一次。

### 4. 并发互踢
`studyTicket` 是服务端注入页面的 GUID，心跳会回吐比对，不等就 `EndSCO` 并提示「检测到正在学习另一课件」。
所以**同一账号并发一定是负收益**：跑得越多，丢得越多。

### 5. 正确率与答题记录矛盾
`crate=100` 但 `interactions` 为空，或题目数量明显少于课件实际题量 → 老师审计一眼可见。

### 6. 平台显式闸门
- `isPausing`：返回 `{"isPausing":true,"pausingMinute":N}`，锁 N 分钟；`0` 表示今日锁定。
- `checkNoCaptcha`：`status==0` 要求滑块，此时脚本必须停下人工处理。

### 7. 校级层面的复核
教师端**没有**「删除学习记录」按钮（已核实 NUIST 帮助文档）。
老师能做的是学习监控、标记「需要关注学生」、调形成性评价权重；
真正的记录清除来自平台侧复核 + 教务人工判定，处置阶梯通常是「清记录 → 冻结 → 取消考试资格」。
这一层没有技术规避面。

## 四、v3.6 做了什么（对策 → 代码）

| 对策 | 代码位置 | 说明 |
|---|---|---|
| 按 `timelitsec` 缺口自动补齐时长 | `welearn_curriculum_submit` | 目标 = max(用户设定下限, timelitsec − useSeconds)，上限 1500s；达标即停表，不空等 |
| 学中持续心跳（20~32s） | `welearn_heartbeat_full` + 提交循环 | 结束再补一次心跳，参数对齐官方（`timelimitsec` / `endcaltime`） |
| 提交后回读校验 | `welearn_verify_learntime` | 以 `startsco.useSeconds` 为真值（课时列表的 `learntime` 有延迟，会误判） |
| 强制单并发 | `_on_start_task` / 输入框 | 并发被强制为 1，界面直接写明原因 |
| 单日上限 + 冷却 | `daily_lesson_cap` / `cooldown_every` | 安全档：24 节/天，每 4 节休息 7~15 分钟 |
| 正确率随机 | 默认 80~92% | 避免「100% 且无答题记录」这种异常组合 |
| 闸门检测 | `welearn_check_gates` | 每节课前查 `isPausing` / `checkNoCaptcha`，命中就停下并提示人工处理 |
| 失败不重试爆炸 | 提交只做一次 + 回读 | 客观题只能提交一次（`retry_count++`），少提交比乱提交安全 |
| 停止即落库 | `stop_check` + 最终心跳 | 停止时先把已学时长落库再退出，不白学（实测 +50s 入账） |
| 未学满不谎报完成 | `reached_final` / `cstatus_val` | 时长不足 95% 时提交 `incomplete` + 实际 progress，避免"秒完成"特征 |

**关键取舍**：时间不能再压缩。
`sco` 的长度是平台定的，想拿 6 学时就得真在线 6 小时；v3.6 只是把这 6 小时**安全地**花掉，
并把「一次刷完」改成「分几天刷完」，避免 T+1 复核命中。

## 五、使用建议（照做能显著降低被打回概率）

1. **别一口气刷完**：安全档单日 24 节；课时多就分 2~3 天。
2. **用安全档，不要用极速档**：极速档只是应急，被打回概率很高。
3. **白天跑**：08:00–23:00，避开凌晨集中完成。
4. **只开一个程序**：同一账号不要同时开浏览器学习页 + 本工具。
5. **按提示停手**：出现 `isPausing` 锁定、滑块验证，立刻停下人工处理。
6. **看回读结果**：日志里 `回读 XXXs` 没到 `平台要求 1080s` 的，下次再跑一次会自动补齐。
7. **别改正确率为 100**：保持随机，且答题记录要能对上题量。

## 六、无法规避的部分（诚实清单）

- 学时的物理下界：`timelitsec` 由课件决定，只能花时间。
- `studyTicket` 单会话互斥：同账号并发必丢时长。
- `seconds` 授予算法在服务端，客户端只能被动接收。
- `isPausing` / `checkNoCaptcha` 是平台显式闸门，触发后只能人工介入。
- 客观题每课时只能提交一次，提交错了不可逆（除非教师端重置）。
- 平台侧复核与校级处置：技术上无解，只能靠「像真人一样学习」降低命中率。
